# 自動決済管理システム

## 1. プロジェクトの背景と目的
### 1.1. 現状の課題
本ゼミナール内で運営している「ゼミカフェ」は、完全セルフサービスかつ現金決済を中心とした小規模運用を行っていますが、以下の運用課題（コスト・手間）が発生していました。
* **アナログ管理の限界:** 10杯先払いサービスにおいて、紙に「正の字」を手書きして残数を管理しており、用紙の印刷やペンの記入といった物理的な手間が生じている。
* **売上データのブラックボックス化:** 現金決済が中心であるため、「いつ・誰が・何を」購入したかという詳細な履歴データが一切残らず、ピークタイムの把握や需要予測といったデータ駆動型（データドリブン）の店舗運営が不可能な状態となっている。

### 1.2. 目的
本プロジェクトでは、**「利用者の操作手間（UXの維持・向上）」**と**「ライトユーザーの心理的ハードルの低下」**を最優先に考慮しつつ、現場のエッジ端末（Raspberry Pi）とインターネット上のクラウドサーバーを連携させることで、**「決済・利用履歴管理の自動化」**および**「データ分析を基盤とした店舗運営のモダン化」**を両立したWebシステムを構築します。

---

## 2. ターゲットユーザーとペルソナ
本システムは、利用頻度に応じて異なるアプローチを提供します。

1. **ライト層（都度払いユーザー）**
   * **特徴:** たまにコーヒーを1杯だけ、またはお菓子だけを購入するゼミ生やゼミ室の訪問者
   * **要件:** 会員登録などの事前準備なしで、ユーザー負担が小さく決済方法が分かりやすいシステムにすること
2. **ヘビー層（10杯先払いユーザー）**
   * **特徴:** 日常的にゼミカフェを利用し、事前に10杯分の代金を支払うゼミ生。
   * **要件:** 紙とペンを使わず、一瞬で「本人識別」と「残数カウントダウン」が完結すること。
3. **管理者（運営メンバー）**
   * **特徴:** カフェの在庫や売上を管理するメンバー。
   * **要件:** 自宅や外出先からでも、スマホやPCのブラウザ経由で最新の経営状況（売上など）を一目で把握できること。

## 3. システムアーキテクチャ
将来的なシステムの機能拡張や遠隔でのデータ統合を見据え、現場のエッジ端末内に処理を閉じ込めない**「クラウド・エッジ分離型アーキテクチャ」**を採用しています。さらに、専任のインフラ保守担当者が不在の環境でも安定して長期間運用できるよう、フルマネージドなBaaS（Firebase）を活用したサーバーレス構成とし、OSのアップデートやデータベース管理といった維持・管理コストを最小化しています。

    [ 現場：エッジ端末 (Raspberry Pi) ]
     ├── 入力・フィードバックデバイス
     │    ├── M5StickC Plus2 (コイン機からのパルス検知 ＋ LCD画面による状態表示)
     │    ├── SONY PaSoRi RC-S380 (学生証読み取り / NFC FeliCa規格)
     │    └── 外部スピーカー (音声案内による直感的なフィードバック)
     └── エッジアプリケーション (Python)
            │    (M5StickCとのシリアル通信 ＋ 学生番号の正規表現抽出 ＋ 音声再生制御)
            ▼ (インターネット経由でのセキュア通信)
            │
    [ クラウド側：BaaS (Firebase) ]
     ├── データベース (Firestore: リアルタイム同期型NoSQL)
     └── 管理者用ダッシュボード (HTML/CSS/JavaScriptによる専用Web UI)

## 4. 学籍番号抽出の仕様について
学生証内の特定のサービスコードへの直接アクセスは、大学側の仕様変更によって保存ブロックが移動した際のエラーリスクを考慮し、採用していません。代わりに`tag.dump()`で取得したダンプデータ全体から正規表現（`[A-Z]{2}\d{5}`）を用いて学籍番号を抽出する方式を採用することで、将来のカードフォーマット変更にも耐えうる柔軟なシステム設計としています。

## 5. コインセレクター制御におけるエッジマイコン（M5StickC Plus2）の分離採用
本システムでは、コインセレクターからの入力をRaspberry Piへ直接接続するのではなく、**M5StickC Plus2を経由して連携する分散構成**を採用しています。これには以下の技術的根拠があります。

1. **リアルタイム性の担保とシビアなタイミング制御**
   Raspberry Piは汎用OS上で動作するため、裏のタスク処理によりミリ秒単位のパルス検知に遅延が生じるリスクがあります。これをリアルタイム処理に優れたマイコン（C++ / FreeRTOS）に委譲することで、確実な信号検知と無効硬貨の即座な返却（リジェクト）制御をハードウェアレベルで実現しています。
2. **ディスプレイを用いた即時的な状態フィードバック (UX向上)**
   最新のM5StickC Plus2を採用し、デバイスのLCDディスプレイをエッジ側のUIとして活用しています。Raspberry Pi上のPythonスクリプトとシリアル通信で状態（通常決済、サブスク利用回数、エラー等）をリアルタイムに連携し、色覚的な変化（緑・赤・オレンジ等）とテキスト表示を組み合わせることで、無人レジにおけるユーザーの不安を払拭する直感的なUXを提供しています。

## 6. クラウド・データベース選定とセキュリティ対策
システム全体のデータ基盤として、エッジ（ラズパイ）単体にデータを保存せず、Googleの**Firebase Firestore (Standardエディション)**を採用しました。これには店舗運営・システム保守・セキュリティの観点から明確な技術的根拠があります。

1. **遠隔からのデータアクセスと分析基盤の構築**
   ゼミ室内に設置されたラズパイに依存することなく、管理者自身のスマートフォンやPCから、いつでもどこでも最新の売上状況を確認・分析できる環境を構築するためです。
2. **障害時のデータ保全（顧客資産の保護）**
   「10杯先払い」という前払いシステムを導入している性質上、万が一ラズパイ本体が故障・破損した場合でも、ユーザーの「残り杯数」のデータを確実に保護する必要があります。クラウド上にデータを分離することで、機器トラブル時にも正確な残数把握と返金対応が可能な耐障害性（フォールトトレランス）を確保しました。
3. **継続的な運用を見据えた保守性とゼロコスト**
   Firebaseを選定した理由は、サーバー構築が不要（サーバーレス）であり、開発・保守の手間が極めて少ない点です。自身が卒業した後でも後輩への引き継ぎ（属人化の排除）が容易であり、小規模運用であれば無料枠内で稼働するため、ランニングコストを永続的にゼロに抑えることができます。
4. **リアルタイム同期と将来的な拡張性の確保**
   Firestore独自のリアルタイム同期機能（`onSnapshot`）を活用し、決済が発生した瞬間に管理画面へ反映される即時性の高いUIを実現しました。また、自動インデックスを備えたNoSQLであるため柔軟性が高く、将来的な売上集計や特定ユーザーの検索、別端末への展開など、システムの拡張（スケーラビリティ）にも強いアーキテクチャとなっています。
5. **認証情報のセキュアな管理（クレデンシャル保護）**
   エッジ（Raspberry Pi）からクラウドへ安全にデータを送信するため、専用のサービスアカウント秘密鍵（JSON）を用いて認証を行っています。また、ソースコードをGitLabで管理するにあたり、`.gitignore` を適切に設定することで、認証キーの漏洩（クレデンシャル・リーク）を未然に防ぐ実務に即したセキュリティ運用を徹底しています。

## 7. リアルタイムWebダッシュボードの構築（フロントエンド）
管理者向けの売上・利用履歴管理画面として、HTML/CSS/JavaScriptを用いたシングルページアプリケーション（SPA）を構築し、GitLabリポジトリにてエッジ側のコードと統合管理しています。

1. **完全なリアルタイム同期の実現**
   Firebase JavaScript SDKの `onSnapshot` メソッドを活用し、ラズパイ側で決済が発生した瞬間に、ブラウザの再読み込みなしでダッシュボードの表が自動更新されるUIを実装しました。これにより、遠隔からでも店舗の稼働状況を瞬時に把握できます。
2. **モダンなUI開発と軽量化**
   CSSフレームワークとしてTailwind CSS（CDN）を採用することで、無駄なビルド環境の構築を省きつつ、短時間で実用的かつレスポンシブなUIを構築しました。
3. **BaaS特有のセキュリティ設計の理解**
   Webフロントエンド側にFirebaseの接続用APIキーを記述していますが、これはBaaSにおける「公開用識別子」であるというアーキテクチャの仕様を理解した上での実装です。実際のデータ保護はFirestoreのセキュリティルールで制御する設計としており、ラズパイ側の秘密鍵（JSON）の隠蔽と合わせて、システムの全層において適切なセキュリティ境界を設けています。

## 8. 店舗運用を見据えた自動起動および耐障害性設計（systemd）
無人店舗の決済端末として安定稼働させるため、Linuxの標準システム管理機構（`systemd`）を利用したバックグラウンドサービス化を実施しました。

1. **完全自動起動（Headless運用）の実現**
   コンセントを刺すだけでユーザーログインや手動操作を一切介さずに決済プログラムが立ち上がるデーモン（サービス）構成を構築し、店舗設置時の運用負荷を極限まで削減しました。
2. **高い可用性と自動復旧（自己修復）機能**
   予期せぬエラーや通信断絶によってプロセスが異常終了した場合でも、`Restart=always`（5秒後の自動再起動）を設定することで、人間が再起動操作を行わなくても自動で正常な待機状態へ復旧する高可用なシステムを実現しました。
